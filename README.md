# BillboardSystem

Система управления сетью рекламных билбордов: клиент покупает размещение, загружает ролик,
оплачивает показы виртуальными деньгами, а устройство получает манифест, скачивает файл
и отчитывается о показах.

Учебный проект команды из трёх человек. Этот репозиторий содержит **полную серверную часть
участника 3** (backend, БД, хранение медиа, финансы) и контракты для интерфейса (участник 1)
и симулятора (участник 2).

## Технологии

- C# 13 / .NET 10, ASP.NET Core Web API
- PostgreSQL 17 + Entity Framework Core 10 (миграции)
- ASP.NET Core Identity (роли `Admin` / `Client`, bearer-токены, отдельная схема для устройств)
- MinIO / любое S3-совместимое хранилище; локальное хранилище для разработки и тестов
- xUnit: юнит-тесты (SQLite) и сквозные HTTP-тесты (`WebApplicationFactory`)
- Docker Compose

## Быстрый старт

### Docker Compose (рекомендуется)

    cp .env.example .env      # задайте пароли и SEED_ADMIN_*
    docker compose up --build

- API: http://localhost:8080
- OpenAPI: http://localhost:8080/openapi/v1.json
- Проверка живости: http://localhost:8080/health

Администратор создаётся при старте из `SEED_ADMIN_EMAIL` / `SEED_ADMIN_PASSWORD`.
Схема БД применяется миграциями автоматически. Для локального запуска Compose хранит видео
в Docker volume и не требует отдельного S3-хранилища.

### Локально без Docker

    # PostgreSQL должен быть запущен, строка подключения — в appsettings
    dotnet build BillboardSystem.slnx
    dotnet run --project src/Billboard.Api

Для разработки без S3-хранилища можно хранить файлы на диске:

    "Storage": { "Provider": "Local", "LocalPath": "./storage-data" }

### Тесты

    dotnet test BillboardSystem.slnx

81 тест: 68 юнит-тестов (кошелёк, резервы, идемпотентность, ёмкость расписания, манифест,
владение, группы, групповое назначение) и 13 сквозных HTTP-тестов (регистрация → видео →
размещение → публикация → показ → отмена, группы, «мои» списки, админ-CRUD, групповое назначение,
локальная отдача видео, отключение билборда и блокировка пользователя).
Сквозные тесты работают на SQLite в памяти и локальном хранилище, Docker не нужен.

### Миграции

    dotnet tool install --global dotnet-ef
    dotnet ef migrations add <Name> -p src/Billboard.Infrastructure -s src/Billboard.Api
    dotnet ef database update -p src/Billboard.Infrastructure -s src/Billboard.Api

Начальная миграция уже в репозитории: `src/Billboard.Infrastructure/Persistence/Migrations`.

## Что реализовано (участник 3)

| Модуль | Что сделано |
|---|---|
| Пользователи | Регистрация, вход, `me`; роли Admin/Client; блокировка пользователя; bearer-токены |
| Билборды | CRUD для администратора, каталог для клиента, отключение, ротация токена устройства |
| Медиатека | Двухшаговая загрузка, импорт по URL с защитой от SSRF, проверка ffprobe, сжатие ffmpeg, SHA-256, лимиты тарифа, запрет удаления используемого видео |
| Тарифы | Старт/Стандарт/Бизнес из ТЗ, лимиты, скидка за несколько билбордов, подписки |
| Кошелёк | Виртуальный баланс, резерв, списание, возврат, история операций, идемпотентность |
| Биллинг | Расчёт стоимости, резерв при публикации, списание за подтверждённый показ, начисления владельцу, автопауза при исчерпании бюджета |
| Показы | Приём событий от устройств, защита от повторного списания, статистика |
| Размещения | Черновик → проверка → публикация → пауза/возобновление → отмена с возвратом резерва |
| Устройства | Манифест с временными ссылками (запись на каждое размещение: `placementId`, квота), отчёт о кэше, конфигурация (лимит 32 ГБ) |
| Группы | CRUD групп билбордов и состав участников (API для админки и клиента) |
| Владение | `OwnerId` у билборда и группы; `?mine=true` — только свои устройства и группы (владение или аренда) |
| Групповое назначение | Одно расписание на группу: проверка всех устройств, черновики «всё или ничего», резерв бюджета |
| Администрирование | Пользователи, журнал действий, CSV-экспорт, мониторинг устройств |

Подробные контракты — в [docs/api-contracts.md](docs/api-contracts.md),
архитектурные правила — в [docs/architecture.md](docs/architecture.md).

## Сквозной сценарий (для защиты)

1. `POST /api/v1/account/register` — клиент регистрируется.
2. `POST /api/v1/account/login` — получает `accessToken`.
3. Администратор создаёт билборд: `POST /api/v1/admin/billboards` → в ответе `deviceToken`.
4. Клиент создаёт загрузку `POST /api/v1/videos/uploads`, затем `PUT /api/v1/videos/{id}/content`.
5. Пополняет баланс: `POST /api/v1/billing/top-ups` с `idempotencyKey`.
6. Создаёт размещение `POST /api/v1/placements`, проверяет `POST /api/v1/placements/validate`.
7. Публикует `POST /api/v1/placements/{id}/publish` — списывается резерв.
8. Устройство с `X-Device-Token` получает `GET /api/v1/devices/{id}/manifest`.
9. Отправляет показы `POST /api/v1/devices/{id}/playback-events` (повтор не списывает деньги).
10. Клиент видит затраты `GET /api/v1/billing/usage`, администратор — доход `GET /api/v1/billing/earnings`.
11. Отмена размещения возвращает неиспользованный резерв на баланс.

Готовые запросы — в `src/Billboard.Api/Billboard.Api.http`.

## Деньги: как это работает

- `Wallet.Balance` — доступные средства, `Wallet.ReservedBalance` — зарезервированные.
  Резерв **переносится** из баланса, а не дублируется: доступно = `Balance`.
- Публикация: `C = ceil(часы × показов_в_час) × цена_показа × (1 − скидка)`.
  Итог округляется вверх до копеек, чтобы резерва хватило на все показы.
- Списание — только по событию `Completed` от устройства и только один раз
  (уникальный `IdempotencyKey` + уникальный индекс в БД).
- Исчерпание резерва: размещение переходит в `Paused` с причиной `BudgetExhausted`,
  клиент видит это в статусе; пополнение резерва возвращает `Scheduled`.
- Все суммы — `decimal(18,4)`, никогда не `double`.

## Границы ответственности

Серверная часть готова к интеграции:

- **Участник 1 (UI/DevOps).** Все эндпоинты описаны в `docs/api-contracts.md`, ошибки
  единообразны (`{ code, message, details }`), авторизация — bearer-токен из `/account/login`.
  Blazor-проект пока содержит шаблонные страницы.
- **Участник 2 (расписания/симулятор).** Реализован серверный манифест (запись на каждое
  размещение) и приём показов; сам симулятор, локальный кэш и офлайн-режим — его зона.
  Проверка расписания вынесена в `IScheduleValidator`: текущая реализация
  `CapacityScheduleValidator` считает ёмкость по часам, полноценный планировщик
  подключается заменой одной регистрации в DI.
- **Группы билбордов.** CRUD, состав и групповое назначение расписания реализованы;
  расширенный планировщик P2 подключается заменой `IScheduleValidator`.

## Ограничения учебной версии

- Платежи имитируются (`MockPaymentService`), реального банка нет.
- Сжатие видео требует `ffmpeg` в контейнере (уже установлен в Dockerfile); без него
  загрузка работает, но сжатие пропускается, а при `Media:RequireProbe=true` загрузка
  требует `ffprobe`.
- Симулятор билборда и веб-интерфейс в этом репозитории пока шаблонные.
