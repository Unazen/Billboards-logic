# Архитектура и правила

Документ фиксирует решения, которые нельзя менять без согласования команды.
Часть из них проверяется тестами (`tests/Billboard.UnitTests`, `tests/Billboard.IntegrationTests`).

## Слои

- `Billboard.Domain` — сущности, перечисления, `IVideoStorage`. Без зависимостей от ASP.NET.
- `Billboard.Application` — DTO, интерфейсы сервисов, чистая логика: расчёт стоимости
  (`QuoteCalculator`), проверки видео (`VideoPolicy`), защита URL (`UrlGuard`),
  ограниченное копирование (`BoundedCopy`), дни недели (`WeekMask`), часовые пояса (`TimeZones`).
- `Billboard.Infrastructure` — EF Core (`AppDbContext`), сервисы, MinIO/локальное хранилище,
  ffprobe/ffmpeg, имитация платежей, проверка расписания.
- `Billboard.Api` — контроллеры, аутентификация, единый формат ошибок, DI.

EF-сущности не сериализуются в API: наружу отдаются только DTO.

## Деньги

Инвариант кошелька: `Balance` — доступные деньги, `ReservedBalance` — зарезервированные.
Резерв переносится из баланса (`Balance -= X; ReservedBalance += X`), поэтому
«доступно» — это всегда `Balance`, а не `Balance - Reserved`.

Все изменения баланса идут через `WalletLedger` — единственное место, где меняются суммы.
Сервисные методы не вызывают `SaveChanges` внутри журнала: кошелёк, транзакция и связанная
сущность сохраняются одной операцией, чтобы не было половинчатых состояний.

Правила:

1. Суммы — `decimal` с точностью `(18,4)`; `double` запрещён.
2. Цена показа фиксируется в `BudgetReservation.PricePerPlay` на момент публикации:
   последующее изменение цены билборда не меняет уже оплаченное размещение.
3. Стоимость: `ceil(часы × показов_в_час) × цена_показа × (1 − скидка/100)`,
   итог округляется **вверх** до копеек, чтобы резерва хватило на все показы.
4. Резерв создаётся один раз на размещение: `BudgetReservation.PlacementId` уникален.
5. Возврат при отмене/завершении: `Release` переводит остаток резерва обратно в баланс.
6. Исчерпание резерва: статус `Paused`, `PauseReason = "BudgetExhausted"`,
   запись `PlacementPausedBudgetExhausted` в журнале — по ней клиент узнаёт о проблеме.
   Видео и размещение не удаляются.

## Идемпотентность

- `WalletTransaction.IdempotencyKey` — уникальный индекс. Ключ формируется как
  `"{userId}:{операция}:{внешний ключ}"` (`WalletLedger.UserKey`).
- `PlaybackEvent.IdempotencyKey` — уникальный индекс, в БД пишется
  `"{billboardId:N}:{ключ устройства}"`: одинаковые ключи от разных устройств не конфликтуют.
- Повторное событие показов не создаёт второй показ и не списывает деньги.
- Конкурентные запросы: при `DbUpdateException` по уникальному ключу сервис возвращает
  уже сохранённый результат, а не 500.

## Показы

- Учитываются только события `Completed`; `Skipped` и `Error` сохраняются, но не оплачиваются.
- Оплата возможна только для размещений в статусах `Scheduled`, `Downloading`, `Ready`, `Active`.
- Начисление владельцу (`OwnerEarning`) уникально по `PlaybackEventId`.
- Событие от чужого билборда отклоняется.

## Проверка расписания

`IScheduleValidator` — точка расширения участника 2. Текущая реализация
`CapacityScheduleValidator`:

- для каждого часа окна считает требуемые секунды: `показов_в_час × длительность ролика`;
- суммирует требования действующих размещений билборда в этом часе;
- сравнивает с `Billboard.AdvertCapacitySecondsPerHour`;
- перекрытие по времени само по себе конфликтом **не является** — важна суммарная ёмкость;
- размещения без известной длительности ролика публиковать нельзя (`VIDEO_DURATION_UNKNOWN`);
- приостановленные из-за бюджета размещения ёмкость не занимают.

Альтернативы — сдвиг окна на час вперёд в пределах двух недель.

## Владение и «мои» списки

- `BillboardDevice.OwnerId` и `BillboardGroup.OwnerId` — nullable владелец (клиент/партнёр);
  `null` означает устройство или группу компании.
- `?mine=true` для билбордов: владение **или** наличие размещения пользователя на устройстве
  (клиент арендует устройство, а не владеет им — так требует план).
- `?mine=true` для групп: владелец группы или аренда хотя бы одного входящего билборда.
- Админские списки (`/admin/...`) не фильтруются и показывают всю сеть.

## Групповое назначение

`POST /api/v1/placement-groups/validate|drafts` — один шаблон расписания на группу:

1. проверяются все устройства группы тем же `IScheduleValidator`;
2. `drafts` создаёт черновики в одной транзакции и сразу резервирует бюджет по каждому;
3. если хотя бы одно устройство не прошло проверку или не хватило денег — откатывается всё;
4. отмена черновика возвращает резерв.

Логика P2 (`GroupPlacementService`) и наши endpoint'ы совпадают по контракту; при
объединении библиотек P2 внутреннюю реализацию можно заменить, не меняя API.

## Хранение медиа

- В БД — метаданные (`VideoAsset`), сами файлы — в объектном хранилище (`IVideoStorage`).
- Ключ объекта: `videos/{ownerId}/{videoId}/original.{ext}`; имя файла пользователя
  в путь не попадает.
- Файл получает статус `Ready` только после проверки размера в хранилище и SHA-256.
- Удаление — мягкое (`IsDeleted`), чтобы не рвать историю размещений и показов;
  удаление запрещено, пока видео используется в активном размещении.
- Устройствам выдаются временные presigned URL; постоянных публичных ссылок нет.

## Безопасность

- Импорт по URL проверяет адрес в момент подключения (`ConnectCallback`), поэтому
  DNS rebinding и редиректы не позволяют обратиться во внутреннюю сеть.
- Токен устройства хранится как SHA-256; в БД нет самого секрета. Сравнение —
  `CryptographicOperations.FixedTimeEquals`.
- Владелец объекта всегда берётся из токена; чужие объекты отдают 404, а не 403.

## Тесты

- `Billboard.UnitTests` — SQLite в памяти, сервисы собираются вручную.
- `Billboard.IntegrationTests` — реальный HTTP через `WebApplicationFactory`, SQLite в памяти,
  локальное хранилище, заглушка ffprobe. Проверяют весь сценарий кампании, идемпотентность,
  запрет удаления используемого видео и изоляцию клиентов.

## Известные границы

- Группы билбордов: CRUD, состав и групповое назначение расписания реализованы;
  расширенный планировщик P2 подключается заменой `IScheduleValidator`.
- Манифест отдаёт размещения, активные в текущий момент, отдельной записью на каждое
  размещение (`placementId`, `minimumPlaysPerHour`); предзагрузка будущих слотов —
  участник 2 (симулятор).
- Подписка списывается с доступного баланса; автопродления нет.
